## Component rules

| Design rules | Checked behavior and evidence |
| --- | --- |
| **C2 BR-2.1**, role and ownership restrictions. | IoT Staff mutate devices/configuration/commands; Cloud Staff inspect; owners' API reads are restricted to their cars. JWT and edge-key authentication are enforced server-side. Device/command tests and the [Docker live checks](evidence/docker-live-verification.json) cover the relevant guards. |
| **C2 BR-2.2**, heartbeat and offline state. | Heartbeats update last seen and position; a 30-second sweeper applies the 90-second offline cutoff. Initial registration does not pretend a device process is connected. Time-based device tests exercise state changes. |
| **C2 BR-2.3–2.4**, Wi-Fi validation and secrecy. | SSID is 1–32 UTF-8 bytes; open networks reject passwords; WPA2/WPA3 require 8–63 characters. Passwords are masked and never prefilled. Fernet protects stored credentials and encrypted edge delivery; public device/history responses omit them. |
| **C2 BR-2.5**, command lifecycle. | Duplicate queued commands return 409; commands move through queued/delivered/acknowledged/failed/expired; a queued command expires after ten minutes. Acknowledgement cannot silently close another device's command. |
| **C3 BR-3.1**, upload validation. | Actual file type, payload size, decoded samples and duration are checked. Valid nonempty WAV/MP3 clips up to 10 MiB and 15 seconds are accepted. Invalid input returns the specified 401/403/413/415/422 response without an accepted record. |
| **C3 BR-3.2–3.3**, durable acceptance and repeat upload. | S3 upload precedes record creation; storage failure returns 503. A repeated clip ID returns the existing receipt. The live Docker check downloaded the accepted clip byte-for-byte from MinIO. |
| **C3 BR-3.4–3.5**, queue and retries. | Atomic claims hold a 120-second lease. Expired leases can be reclaimed; stale workers are fenced. Automatic attempts stop at three, then only Cloud Staff can retry a failed record. Tests cover failed-state/role guards, lease recovery and retry. |
| **C3 edge buffering**, durable FIFO. | Up to 200 clips persist on disk, retain stable clip IDs and flush in order after recovery. Failed sends leave clips buffered; overflow refuses a new capture rather than silently discarding an accepted clip. |

The [final portable CARLA-to-component verification](evidence/carla-verification.json) passed matching client/server and advancing-world checks, two Start/Stop cycles with GPS resumption/changing images, all five recorded inputs processed into alerts, and SHA-matching audio downloads. Both actual stops reached below 0.1 km/h. The tested host profile uses the default map, fixed 0.05-second physics and launcher-scoped Intel settings; runtime world travel is avoided.

Wi-Fi configuration, validation, encrypted delivery and command acknowledgements work through the component. Applying settings to a physical operating system requires the real edge device's `wifi_apply` callback. The default CARLA adapter saves the encrypted configuration and reports unsupported OS application; it does not claim to change the host network. Physical reboot is likewise unsupported by that raw adapter. The local edge and owned CARLA demo unit can acknowledge simulated device configuration/reboot; neither changes the host operating system or network.

The five bundled recordings exercise the complete path; scenario labels are input metadata, while the model chooses its prediction. The horn and rain examples have documented low-confidence classification errors and enter anomaly handling. These examples do not establish held-out model accuracy. Model management is shown as shared C4/C5 integration.
